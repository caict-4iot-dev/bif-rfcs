### 2. 摘要
--------
本协议规范定义星火链网二层网络的技术接入标准，明确第三方区块链二层的兼容性、安全性与互操作性要求。通过架构设计、数据格式、验证流程等标准化，确保生态内同构、异构链协同运行，并为评测提供统一技术框架，推动开放生态的规模化发展。

### 3. 动机
--------
区块链二层扩容方案不仅用于扩容和降本，以满足AI、游戏、数字资产等业务对性能的需求，还能用于构建数据隐私应用和企业私有区块链，更容易地围绕核心的区块链做多链生态。因此，二层扩容方案对星火链网的技术发展和生态建设具有重要价值。

现有区块链二层方案技术异构性强，生态协同不足，制约跨链互操作与规模化应用。制定统一接入协议旨在降低开发者门槛，保障链间数据可信互通，通过标准化评测体系筛选合规方案，加速星火链网生态的技术融合与产业落地，赋能多场景高并发需求。

##### 4.1.4 支持异构二层链
星火一层区块链节点的合约层有个二层管理组件，是部署在星火一层区块链的智能合约，代表星火一层区块链实现对二层区块链的管理。

星火二层网络对二层区块链的技术架构不做特定要求，只要其提交的区块数据能被一层网关和星火一层区块链正确识别和处理即可。数据的适配由二层网关负责。对于与星火一层区块链同构的二层区块链，其技术架构基本与星火一层区块链相同，区别只是合约层不需要二层管理组件。

#### 4.2 核心角色
星火二层网络架构的核心角色有4个，分为一层和二层两个层次，其中位于一层的是一层区块链和一层网关，位于二层的是二层区块链和二层网关。

![](https://cdn.nlark.com/yuque/0/2025/png/48636428/1741916260358-6ef3c283-3759-409d-9a89-ca8d28a24355.png)
<p align="center">
图 5 核心角色及其关系
</p>
##### 4.2.1 二层管理组件
二层管理组件是部署在星火一层区块链的一套智能合约，负责为每个接入的二层区块链创建一个管理实例，负责管理二层区块链的参数和活性，以及对二层区块链的执行结果做处理。二层管理组件的另一作用是作为二层区块链的运营方管理二层区块链的工具。

##### 4.2.2 二层区块链
二层区块链网络中的节点分为两种，一种是执行节点，负责生成区块；另一种是验证者节点，负责监督执行节点。执行节点之间通过共识算法保持区块的一致性。验证者节点被设计为开放的节点程序，任何主体都可以作为验证者加入二层网络，对执行节点进行监督。

星火二层网络既支持与星火一层区块链同构的链，也支持基于以太坊的链以及其他异构区块链作为二层区块链接入到星火二层网络生态。

##### 4.2.3 一层网关
一层网关由星火一层区块链的超级节点运营，每一个接入星火一层区块链的二层网络独立部署一个一层网关。一层网关有两个作用，一个是负责与二层网关进行通信，包括上传二层状态数据到一层区块链、通知网关二层区块确认情况等；另一个是负责存储二层区块链网络的区块数据，并提供给验证者节点做验证。

##### 4.2.4 二层网关
为支持异构区块链作为二层接入，考虑到不同区块链采用的区块结构、账户状态、API接口等存在差异，因此设计了二层网关这个角色，来完成二层区块链数据结构适配以及区块和状态数据上传。同时，一层网关和二层网关之间采用统一的数据通信协议。

#### 4.3 基本原理
##### 4.3.1工作机制概述


![](https://cdn.nlark.com/yuque/0/2025/png/48636428/1741916260607-60adb885-72b6-4b42-9b7b-e82347bf208f.png)
<p align="center">
图 6 星火二层网络工作机制
</p>
星火二层网络的工作机制如图 6所示。将星火核心共识网络（又称为一层区块链/L1）的计算过程转移到二层区块链（L2）进行，计算结果存储在一层的共识网络。由于一层区块链负载减小，因此能达到扩容的目的。其中：

1. 一层区块链作为信任层，负责对二层交易状态的最终确认，保证网络整体的安全性。
2. 二层区块链为星火一层区块链提供执行性能和数据存储的可扩展性。其中，执行节点负责执行二层交易，并向一层提交数据（交易列表和区块），由一层保证二层网络的数据可用性。验证节点负责校验二层的执行结果，保证二层网络的数据安全性。

二层管理组件管理多个二层实例，每个二层实例里保存了网关的数据，以及二层提交状态数据的信息。二层运营又叫作超级账户，通过调用二层管理组件的接口来实现对二层网络的管理，比如注册、更新、停用和重启等操作。之所以在模块设计中加入一层网关和二层网关两个角色，是因为要解决异构二层的兼容性问题，以及缓解主网吞吐量瓶颈带来的存储负担。

星火二层网络正常运行的一般流程是，对于二层区块链产生的每个或者每一批区块：

1. 二层区块链的执行节点提交二层区块到二层网关。
2. 二层网关根据区块信息签署一笔新交易，该交易包含了区块头，并将该交易与区块提交给星火一层网关。
3. 星火一层网关缓存该区块，并将交易发到星火一层的节点，即星火一层的某个超级节点。
4. 星火一层上对该交易做共识并执行，该交易将调用二层管理组件，触发二层网络对应的二层实例的状态数据更新。
5. 二层实例更新成功后，网关将日志事件通知到二层区块链网络。

在星火二层生态中，星火一层区块链处于核心地位，为二层区块链提供安全性和信任。首先，二层区块链的交易数据提交到一层网关并由一层网关对验证节点提供可访问性，区块状态即执行交易获得的结果数据被提交到一层区块链并由二层管理组件来提供可访问性。则任一验证节点均可以在本地执行交易，以确认二层区块链节点的执行结果是否正确。其次，如果验证节点发现二层区块链节点提交到一层区块链的区块执行结果不正确，则可以触发白名单节点做验证，通过多签技术、欺诈证明等技术来使得二层管理组件识别错误并纠正错误。

一层网关与二层管理组件的数据交互有多个情形。（1）一层网关提交二层区块状态到二层管理组件，这是通过向一层区块链提交一笔交易来实现的，采用星火一层数据通信协议；（2）一层网关接收来自二层管理组件中涉及二层实例状态的事件通知，该环节采用星火一层订阅协议。并且待确认区块状态已由状态合约交易确认上链后，采用星火一层订阅协议通知网关删除数据库中已确认的交易列表和区块状态；（3）如果二层管理组件判断状态交易无效，则通过星火一层订阅协议通知一层网关交易丢弃。此时一层网关删除对应的区块，并通知二层网关重提区块数据。

##### 4.3.5 错误证明的数据交互
错误证明用于识别二层区块链和二层网关提交的数据存在的错误（例如区块交易数据与区块状态数据不一致），并通知二层管理组件纠正该错误。验证节点首先处理请求交易数据，识别错误并生成证明，通过一层网关将错误证明提交至二层管理组件；之后二层管理组件请求状态数据进行二次验证，确认错误细节后触发纠正流程，最终确保数据的完整性和正确性。整个过程通过分层协作实现错误检测、证明传递、数据复核及纠正的闭环管理。

### 5. 规范
--------
#### 5.1 网关启动时序的规范
二层网关启动后，主动向一层网关请求其保存的二层网关的状态，并基于此数据继续上报后续区块数据。然后根据网关初始化数据，向二层节点发起区块请求，并上报一层网关。等待一层网关回复，并根据回复结果判断后续操作。

#### 5.3 二层节点与二层网关的交互规范
二层网关获取和处理二层区块数据。二层网关向二层节点请求区块数据。区块数据中包含交易数据和区块头，区块头中包含区块状态，即区块哈希。二层网关对来自二层节点的区块交易数据和区块状态数据做处理，转换成一层网关能识别的数据（见5.4节的SubmitLedgerAndState），为提交给一层网关做准备。

要求二层网关能够及时获取二层节点产生的最新区块，并做正确的数据转换处理。不对具体的实现方案和网络协议做要求。

#### 5.4 二层网关与一层网关的交互规范
##### 5.4.1二层网关向一层网关提交数据的规范
一层网关向二层网关提供如下两个接口：

| **接口** | **描述** |
| --- | --- |
| submit | 用于向一层网关提交二层节点的区块和状态数据 |
| getStatus | 用于查询与一层网关配对的二层网关的状态 |

<p align="center">
表 2 一层网关向二层网关提供的接口
</p>
（1）其中submit的Ledgers字段是protobuf结构SubmitLedgerAndState序列化后得到的字符串，该protobuf结构定义如下：

```
message SubmitLedgerAndState{
    LedgerAndState ledger_state = 1;   //二层区块数据  
    Signature sign = 2; //二层网关针对区块数据做的签名
}
message LedgerAndState {
    int64 seq = 1; // 二层区块序号
    bytes block_header = 2; //二层区块头
	Signature header_sign = 3;  //二层区块头的携带的签名
    bytes block = 4; // 二层区块携带的交易数据
    string metadata = 5; //二层区块携带的元数据
    bytes header_hash = 6; // 二层区块头哈希
}
message Signature {
	string public_key = 1; // 公钥地址
	bytes sign_data = 2; //签名数据
}
```


其中签名数据Signature sign是二层网关节点对LedgerAndState ledger_state的签名，以供一层网关验证二层网关身份。

针对异构二层区块链的情形，只要将需要将异构二层区块数据转换成SubmitLedgerAndState格式即可。

一层网关收到SubmitLedgerAndState数据后，先检查签名，通过后将二层区块状态数据提交到位于一层的二层管理组件，将二层区块数据保存。

#### 5.5 一层网关与二层管理组件的交互规范
##### 5.5.1一层网关向二层管理组件提交交易的规范
一层网关将二层区块状态封装到一笔一层交易中，提交给二层管理组件处理。该交易调用二层管理组件的方法是submitlayer2state，参数是InputSubmitLayer2State类对象。InputSubmitLayer2State类定义如下：

```
message InputSubmitLayer2State{    
    int32 id = 1; //该二层实例的编号
    string bid = 2; // 一层网关的标识符
    int64 seq = 3;
    string block_header = 4;
    Signature header_sign = 5;
    string header_hash = 6;
}    
message Signature {
	string public_key = 1;
	bytes sign_data = 2;
}
```


其中属性id是二层实例的编号，该编号由一层的二层管理组件负责管理；属性bid是二层实例的标识符，也由二层管理组件负责管理；属性header_sign是透传的来自二层网关的签名。

##### 5.5.2 一层网关处理二层管理组件事件的规范

### 7. 风险及应对
-------
#### 7.1 通过星火二层网络来间接攻击星火一层的风险及应对
星火二层网络通过模块化设计来隔离风险。首先由于通过一层网关将星火一层与二层网关、二层区块链隔离。其次，星火一层上部署的二层管理组件，只是新增部署的系统合约，不影响其他系统合约和传统合约。最后，二层管理组件管理的多个二层实例，是相互隔离的，一个二层实例的故障不会影响到其他二层实例。因此，星火二层网络不会对星火一层造成风险。

#### 7.2 星火二层网络本身被攻击的风险及应对
通过攻击二层区块链节点，或者网关，使得向星火一层的二层管理组件提交的数据与二层区块链不一致。针对该问题，首先，星火二层网络可以兼容各种故障证明方案，以在一定时间内及时发现错误；其次，星火一层的二层管理组件提供相关接口，允许白名单用户对二层实例进行冻结、解冻和更新，以避免或者纠正攻击者的影响。
